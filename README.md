# schedule

Сервис для чтения фактически отработанных смен из графиков Google Sheets и последующей синхронизации с облачным Битрикс24.

Сейчас реализованы разбор выгрузки графика, подсчёт уникальных смен,
определение стадии сотрудника и безопасный REST-клиент Битрикс24.

## Правила статусов

- отметка `з` означает заселение;
- отметка `ОВ` / `ов` означает окончание вахты: это не смена, но желаемая
  стадия сделки становится `Вахта завершена` (`WON`);
- смены считаются с даты заселения, а при отсутствии отметки — за всю доступную историю;
- несколько числовых записей одного сотрудника за дату считаются одной сменой;
- 0 смен после заселения: `Заселен` (`PREPARATION`);
- 1–4 смены: `Отработал 1 смену` (`UC_L9233X`);
- 5 и более: `Адаптирован (отработал 5 смен)` (`PREPAYMENT_INVOICE`).

## Секреты

Скопируйте `.env.example` в `.env` и заполните значения локально. Никогда не
добавляйте `.env`, OAuth-файлы или адрес входящего вебхука в Git, сообщения и
журналы. Если вебхук был опубликован, удалите его в Битрикс24 и создайте новый.

По умолчанию изменения сделок запрещены: `BitrixClient.update_deal` требует
явного параметра `allow_write=True`. До проверки предварительного отчёта его
включать нельзя.

Проверка вебхука и созданного поля без изменения CRM:

```powershell
python -m schedule.check_bitrix
```

Подтверждённые настройки портала:

- направление «Вахта»: `BITRIX_CATEGORY_ID=0`;
- количество отработанных смен: `UF_CRM_WORKED_SHIFTS`;
- дата последней смены: `UF_CRM_1715687520`.

Для персональных уведомлений в MAX задайте `MAX_REGISTRY_PATH` — путь к SQLite
базе с привязками `bitrix_user_id` → `max user_id`. Для локальной установки
используется `secrets/max_registry.sqlite3`; если переменная не задана,
программа возьмёт пустую локальную базу `runtime/max_registry.sqlite3`.
Если у менеджера объекта нет привязки к MAX, fallback-уведомление отправляется
только пользователю из `MAX_ADMIN_USER_ID`; общий чат для такого fallback не
используется.

Старые поля «Кол-во смен», «Количество смен» и «Фактическое кол-во смен» не
используются.

## Чтение Google Sheets через браузер

Программа использует отдельный профиль Chrome в `.browser-profile`. При первом
запуске войдите в Google в открывшемся окне:

```powershell
python -m schedule.google_login
```

Предварительная выгрузка и подсчёт без изменений в Битрикс24:

```powershell
python -m schedule.google_export
```

Скачанные рабочие копии сохраняются только в `runtime/`; обе папки исключены из
Git. Пароль Google программа не читает и не хранит — сохраняется браузерная
сессия выделенного профиля.

## Локальная проверка

Сопоставление для `schedule.dry_run` и `schedule.stage_mismatch_report`
выполняется отдельно по объектам из `config/sheet_objects.csv`. Объект сделки
читается из `UF_CRM_642A972B79B02`, дата заселения — из
`UF_CRM_1684488791039`. Начало подсчёта — наиболее поздняя из даты начала
периода, даты заселения CRM и последней отметки `з` на этом объекте.
Неизвестный объект, неоднозначная сделка, пустая/ошибочная или будущая дата
заселения требуют ручной проверки. Смены с другого объекта не переносятся.

Пересчёт отчёта без записи в CRM:

```powershell
python -m schedule.stage_mismatch_report
```

В отчёте `not_found` означает только реальное отсутствие подходящей сделки после
проверки умных совпадений. Сделки, найденные в закрытых или неподходящих стадиях,
старые сделки до начала периода и сделки на другом объекте выводятся отдельными
причинами: `outside_allowed_stages`, `created_before_period` и `wrong_object`.

`SCHEDULE_USE_CACHED_XLSX=1` пересчитывает сохранённые выгрузки, а не свежие
Google-таблицы. `SCHEDULE_START_DATE` и `SCHEDULE_END_DATE` задают включительные
границы периода. Перед реальным обновлением необходимо получить свежие графики.

```powershell
$env:PYTHONPATH = "src"
python -m unittest discover -s tests -v
```

Предварительный разбор скопированного из Google Sheets TSV-файла:

```powershell
python -m schedule.cli path\to\schedule.tsv --source-id document-id
```

Команда выводит распознанные смены в JSON и ничего не отправляет во внешние системы.
